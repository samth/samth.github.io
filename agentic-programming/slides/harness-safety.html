Making the harness safe

What can happen when the model chooses the wrong action?

Today we change the harness around our agent. The two working examples are in Racket: a restricted computation tool and a disposable Python workspace. Press S for speaker notes. Suggested timing: 10 minutes threat model, 15 minutes computation demo, 15 minutes container demo, 10 minutes discussion.

Start with our agent

user → model → tool call → execute
         ↑                   ↓
         └──── tool output ───┘

The model proposes an action.
The harness decides what authority that action gets.

Open the original agent-repl.rhm. Locate the shell invocation and the line that adds its output to messages. Ask students where a command can read files, send data, or change the machine. Do not run an attack through the unrestricted agent.

One tool can have enormous authority

subprocess.run_shell(command)
  • Read the user’s files and environment.
  • Edit or delete everything the process can write.
  • Start programs and make network requests.

Removing one API key from the environment closes one route.

This is an excerpt from the existing Rhombus agent. Its shell inherits our operating-system permissions. Removing REALLMS_API_KEY does not remove other secrets in files, other environment variables, or authenticated programs. Tool count alone is a poor measure of authority.

We trust the harness, runtime, installed libraries, container image, and host.

We are containing code proposed by a model, including code influenced by malicious content. These are teaching examples, not a proof against runtime or kernel exploits. The model request and conversation history are outside the tool sandbox.

Anthropic · Prompt injection guidance

This is a synthetic attack string; do not read an actual secret for the demo. Ask why a correct parser or a useful test runner would not make its text trustworthy. A harness must remain bounded even when the model follows the injected instruction.

Put the boundary outside the model

“model behavior is not a security control”

A prompt can ask the model to behave.
A sandbox restricts what its chosen program can do.

Anthropic · Security risks and sandbox boundaries

Our system prompts still say to treat tool output as untrusted. That is useful guidance, but the file, network, and resource restrictions do not depend on the model obeying it. Approvals, sandboxing, and good model behavior serve different purposes.

Two useful boundaries

Computation agentWorkspace agent
One toolRacket expressionsPOSIX shell
Useful forCalculations, pure functionsPython files and tests
StateFresh each callFiles persist per session
BoundaryRacket sandboxDocker container
Both agents use the same small Racket conversation loop and REALLMS. The implementation is split so the loop and the enforcement are separately readable. Neither tool can read arbitrary host files. Neither requires the model itself to run inside a container.

The trusted client keeps the key

host:   conversation + REALLMS client + API key
                      ↓ code
sandbox:           computation
                      ↓ bounded text
host:              tool result → REALLMS

Give the tool only the capabilities its task needs.

The tool sandbox receives no model API key. The Racket evaluator gets an empty environment. Docker receives a deliberately constructed environment and no host mounts. Code and data supplied in the prompt are intentionally sent to REALLMS.

Racket · Security considerations

The test suite defines a custom printer that tries to write a file. The denial occurs while printing, under the same sandbox. Fresh namespaces alone would not constrain any of this. Already-open ports can also carry authority: do not pass arbitrary host ports into evaluation.

A Racket guard is not an OS sandbox

A guard checks operations performed through Racket.

Giving a native shell permission to start does not make its later file accesses pass through that guard.

For a shell tool, put the process inside an operating-system boundary.

Racket · Security Guards

The language tool denies subprocess execution. The workspace tool uses Docker instead. This distinction is essential: surrounding a shell launch with a path guard would give a misleading sense of containment.

Docker · Runtime constraints

Open make-container for the complete arguments, including the two tmpfs mounts, --pull=never, --init, and --rm. The Docker CLI environment contains only PATH; explicit HOME is added inside. The official Python image is pinned by digest and pulled as a trusted setup step.

Filesystem and network are separate

“effective sandboxing requires both filesystem and network isolation”

No host mounts protects host files.
No external interface blocks direct network connections.

Anthropic · Beyond permission prompts · October 20, 2025

Ask which restriction stops reading a credential and which stops sending it with curl. Neither alone addresses every path. Our container still has loopback. Read-only files can still be disclosed; read-only is not confidentiality.

Tool output is another network path

permitted input → tool output → conversation
                                     ↓
                                model service

A network-isolated tool can still return data to the harness.

Only give it data you intend the model to receive.

Anthropic · Sandbox boundaries and data exposure

This is why no host mount is a meaningful design choice. If we later add repository access, every readable file may become model input. An allowlisted API host would also not automatically constrain what credentials can do at that host.

Contain resource use too

LayerThis example
Tool input / output8,192 characters / 16 KiB capture
Tool attempts8 per user turn, including invalid calls
Racket evaluation2 seconds, 64 MiB
Container command10-second timeout; container removed on timeout
Container lifetime15 minutes maximum
Output is capped while streaming, not after buffering everything. Container output has a short status/truncation suffix. The HTTP request deadline is 120 seconds. Conversation history and model-response size are not globally bounded in these small examples; production use needs those additional limits.

Cleanup is part of the boundary

(dynamic-wind
  void
  run-conversation
  (lambda () (stop-container container)))

End the container, not just the Docker client.
On command timeout, discard the entire workspace.

The tool kills the whole container on timeout because descendants may remain after a shell exits. Normal EOF, exceptions, and interrupts run cleanup. A hard-killed harness may not run its cleanup; the container’s sleep 900 plus --rm bounds that residual lifetime. Runtime or daemon failures are outside that guarantee.

Test allowed work and denied work

Should workShould fail or stop
Compute a statisticRead an ungranted file
Create a Python moduleConnect to the Internet
Import it on the next callWrite outside the workspace
Run assertionsLoop, fill disk, flood output

Run the backend tests without asking the model’s permission.

The test file covers 12 language/output cases and 8 Docker cases. It includes custom printing and timeout cleanup, not just an expected refusal string from a model. A passing test is evidence for that behavior, not proof of absence of all sandbox escapes.

Approvals extend authority

“Run shell commands forever” grants a large capability.

“Apply this reviewed patch to this repository” names a specific action and target.

The next feature could be an explicit, reviewed export step.

Our examples do not apply patches or publish anything. A real workflow could produce a bounded patch, review it outside the sandbox, and then deliberately apply it. Granting a writable host repository mount changes the security policy even if the prompt is unchanged.

What remains trusted?

  • The harness and its API credentials.
  • The Racket runtime and permitted libraries.
  • The container image, daemon, runtime, and host kernel.
  • The review process for any exported result.

Docker · Engine security

Docker access is powerful; this harness is a trusted Docker caller. The container never receives the socket. These examples are appropriate for inspecting boundaries in class, not independently audited hostile multi-tenant execution. Prompt correctness, code correctness, and containment are separate questions.
