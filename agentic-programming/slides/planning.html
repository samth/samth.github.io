Proposed behavior: restore the cursor associated with the edit.

The last two rows are acceptance criteria for the future feature, not a transcript from the current code. Undo restores the pre-insert cursor, redo the post-insert cursor, even if the user moved later. Ask students for a competing reasonable contract.

Our first specification

  • Each nonempty insertion creates one history entry.
  • Cursor movement and empty insertion create none.
  • A new nonempty insertion clears redo history.
  • Empty undo/redo do nothing. Both return this.

Keep UTF-16 offsets. No persistence, edit grouping, or UI yet.

Also preserve redo after moveTo or insert(""). Input policy remains the current string-only use case. Do not turn the demo into unrelated API redesign. Record these decisions so the coding phase does not need to guess.

These are design tradeoffs, not measured performance claims. JavaScript strings may share internal storage. Snapshot history is a teaching baseline, not a guarantee of a full physical copy per edit.

A practitioner’s workflow

Addy Osmani · My LLM coding workflow going into 2026 · January 4, 2026

This is the author’s own workflow. Separate specification (what should happen), plan (how to get there), and validation (how we will tell). The quoted text is a section heading.

The implementation handoff

Implement the agreed snapshot plan. Keep the existing API and string offsets. Add tests for our traces and history branching. Run the tests and report any differences from the plan.

Review the plan before switching into implementation.

Approve implementation in the client. Keep scope small. If time is short, stop after the first test and inspect the expected failure. An alternative is to use the illustrative plan without waiting for a live model.

Evidence for the feature

  • Insertion, undo, and redo restore the specified states.
  • Undo, then a new insertion makes redo unavailable.
  • Cursor moves and empty insertions preserve redo.
  • The cursor stays between zero and the text length.

Check the observed text and cursor, not private stack fields.

For generated traces, model text, cursor, and edit history. A naive law “insert then undo restores everything” misses redo-history changes. Compare the promised observable text and cursor with appropriate preconditions.

Replanning with evidence

  1. Keep the behavior contract and its tests.
  2. Measure snapshot history on the specified workload.
  3. Compare edit records using the same trace.
  4. Choose a representation and rerun the checks.

1,000 full 5 MiB copies would be about 4.9 GiB.
That is a copy-model estimate, not a measured JavaScript heap size.

Actual V8 retention depends on representation and sharing. Measure heap and latency after warming up and use identical operations. Edit records reduce logical history payload, but insertion still operates on a large string. Do not claim that changing history solves all editing costs.

When planning earns its cost

More planning helps when…A short request may suffice when…
Several behaviors seem reasonableThe intended diff is already clear
Choices affect many later stepsThe change is local and reversible
Failure is expensive to detect or undoOne direct check establishes success

This is a synthesis of the tradeoff, not a guaranteed rule. A one-line change can still be risky. End the planning phase when remaining uncertainty is cheaper to resolve with a small test or implementation experiment.

Your turn

Plan a change to your project, or add grouped undo to the buffer.

  1. Write one ambiguous request.
  2. Have the agent inspect and ask questions.
  3. Agree on behavior examples and a short plan.
  4. Trade plans with a partner. Find one hidden assumption.
Suggested eight-minute exercise. For grouped undo, decide how callers mark a group and what nested/empty groups mean. Deliver a short plan and at least two acceptance examples. Do not implement until the partner can explain what completion means.

Before implementation

  • Can we explain the behavior using an example?
  • Does the plan match the repository we inspected?
  • Does each step produce something checkable?
  • Do we know which discovery would change the plan?
Use these questions to review the actual live plan, not only the prepared one. A long document is not inherently more complete. The point is to make the consequential decisions inspectable.
